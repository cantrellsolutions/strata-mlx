# strata-mlx 优化记录

本文记录 strata-mlx 在模型和引擎层面做过的每一项优化:做法、依据、实测结果,以及试过但无效的方向。
逐条实验的原始记录在 `ROADMAP.md` 的 "Faster answers" 一节和 `bench/experiments/e01–e29` 各文件的开头,
原始数据在 `bench/results/`。

- 机器:14 寸 MacBook Pro,M4 Max,128 GB,macOS 27,MLX 0.32.3
- 模型:Qwen3.8-Flash-Next,ISTA-DASLab 的 GSQ-RCO GGUF(与 Strata 用的是同一批文件)
  - Q2_0:66.4 GB(权重 37.6 GB + n-gram 表 28.8 GB),平均 2.4 bit/权重
  - IQ3_S:83.6 GB(权重 54.8 GB + 同一张 n-gram 表),平均 3.5 bit/权重
- 草稿头(MTP):来自原始 16 位检查点的 31 个张量,4.9 GB,不在 GGUF 里
- 除特别说明外,速度都是贪心解码、带思考、每个提示生成 256 个 token
- 运行时内存(MLX 数组,实测):Q2_0 39.5 GB,读过一个提示后 39.7 GB;IQ3_S 56.0 GB,读过一个提示后
  59.4 GB;草稿头另加 1.6 GB(磁盘上 4.9 GB,它的专家装进内存时压成 4 bit)

## 2. 速度的上限由什么决定

先说结论,因为它决定了后面所有优化的方向:**一步的时间主要花在"读多少字节的权重"上,其次是"每个权重做
多少次运算"。**

一个 token 走一遍 48 层要读的权重(Q2_0):

| 部分 | 每个 token 读取 |
| --- | ---: |
| 残差连接(hyper-connection),16 位浮点 | 1.27 GB |
| 线性递归层(Gated DeltaNet)的投影 | 2.1 GB |
| 注意力层的投影 | 0.6 GB |
| 输出层(248,320 × 2,560) | 0.5 GB |
| 其余稠密层 | 0.4 GB |
| 路由专家(每层 512 选 10) | 0.66 GB |
| 合计 | 5.5 GB |

- 用最简单的内核把这些数组各读一遍需要 13.9 ms(约 350 GB/s)。单 token 一步等 GPU 的时间是约 20 ms,
  已经在这个下限的 70%。
- 模型有 1,250 亿参数,但每个 token 只用到约 60 亿;36 层是线性递归层,状态大小固定,所以上下文再长,
  单步时间也几乎不变。
- 窗口里放 4 个 token 时,稠密权重仍只读一遍,只有专家要按 token 各读一份,所以 4 个 token 只比 1 个贵
  约 45%。这就是"先猜再验"划算的原因。

这一点我一开始判断错了:最初以为每个 token 只读约 2 GB,其余时间是"几千个小内核的调度开销",于是做了
三轮内核合并,内核数减了 43%,时间只降了 15%。量出真实字节数之后才转向"少读字节、少做运算"。

## 3. 各项优化

每项给出:做了什么、为什么有效、实测、代码位置、对应实验。

### 3.1 权重的存放方式

**直接读 Strata 的 GGUF,不重新量化**(`strata_mlx/gguf.py`、`load.py`)
- 文件里十几种量化格式,每种都对照 gguf-py 的参考解码做了测试,权重值不变。
- n-gram 表(28.8 GB)留在磁盘上按行读,不进内存:常驻内存 41 GB,启动 22 秒。同一文件用未改动的
  mlx-lm 加载要约 81 GB、约 160 秒(第三方 PR 的数字)。

**专家直接在文件的原始数据块上计算**(`blocks.py`)
- 码本格式(IQ2_S、IQ3_S、IQ3_XXS、IQ4_NL 等)MLX 没有精确的对应格式,展开后 IQ3_S 的专家要 94 GB;
  按文件原样放进 GPU 是 50 GB,由自写的 Metal 内核直接读。九种格式。
- Q2_0 也走这条路:逐 token 38–40 → 41–43 tok/s,加载 34–57 → 22 秒。

**Q6_K 稠密层:每个权重存 1 字节,系数照搬文件**(`dense.py`,实验 e20–e23)
- 起因:Q6_K 每 16 个权重一个缩放系数,MLX 的量化格式最少 32 个,加载器只好把它展开成 16 位浮点。
  IQ3_S 文件有 1.88 GB 的 Q6_K,展开后 4.58 GB,每个 token 读一遍,草稿头每猜一次还要再读 1.27 GB 的输出层。
- 做法:权重 = 编码 × 系数 × d。编码(6 bit)存成一个有符号字节,系数和 d 用文件里的原值。同一个数,
  8.56 bit。内核的线程布局照 MLX 自己的量化乘法:32 个线程分担 4 行,每次各取 8 个权重。
- 实测(整步,与 16 位浮点交替对比):1 / 2 / 4 / 6 / 8 个 token 的窗口分别 −4.0 / −3.5 / −3.2 / −1.4 /
  +1.7 ms。内存 4.58 → 2.45 GB。
- 读提示时仍用浮点:一块提示有上千个 token,MLX 的浮点矩阵乘法在这个规模上最快。浮点权重在第一次读
  提示时由一个内核从三部分算出(12 ms),之后留着:IQ3_S 多占 3.3 GB,Q2_0 多占 0.2 GB(实测)。
  每个提示重算一遍不行:每次新分配几 GB 内存,读提示慢一成(320 对 355–369 tok/s);用 MLX 运算现场展开
  更慢(246 tok/s)。这是和其他引擎对比时才发现的退步。
- 比较过的另一种做法:直接读文件数据块(6.56 bit)。1–2 个 token 时更快,4 个以上更慢,因为每个权重都要
  先把交错存放的位拼回来。没有采用。

**限制 MLX 的缓冲池**(`load.POOL`)
- MLX 把释放的缓冲区留着复用,默认没有上限:读 7,000 token 的提示后池子涨到 65 GB,加上 41 GB 权重,
  机器开始换页,读提示掉到 60–100 tok/s。设成 4 GiB 后恢复到 320–415 tok/s,解码速度不受影响。

### 3.2 先猜再验(draft-and-verify)

**草稿头 + 验证窗口 + 回滚**(`engine.py`、`mtp.py`)
- 模型自带一层"草稿头",猜后面几个 token;主干一次验证整个窗口,只保留猜对的前缀,再把各种状态
  精确回退到"逐个解码这些 token 会留下的状态"。
- 实测:每次验证产出 2.9–3.7 个 token,速度是逐 token 的 1.7–2.2 倍。
- 采样(温度 > 0)时也能用:每个位置的随机数只由种子和位置决定,所以同一个种子带不带草稿写出同一段文字
  (`sampler.py`)。

**猜几个:按草稿头的把握决定**(`drafting.py`,实验 e13)
- 固定先猜 3 个;草稿头对这一串猜测的把握(各猜测概率之积)够高,就再两个两个地猜。运行中统计"各档
  把握的猜测实际被接受的比例",按"多猜一个预期多得多少 token、多花多少毫秒"决定。
- 实测:散文 +2%,代码 +5%,推理 +6%,改代码 +10%。

**从上文抄草稿**(`drafting.py` 的 `Lookup`)
- 回答重复上文时(比如重印整个文件),直接把上文接下来的 token 当猜测。
- 草稿头固定猜 3 个时,改代码 +7%;草稿头"按把握猜"之后不再有收益,所以服务器只在没有草稿头时默认开启。

**猜测只算输出层里"见过的行"**(`rows.py`,实验 e25–e28)
- 起因:每猜一次要算输出层全部 248,320 行,3 次猜测占一步 37–43 ms 里的 2.9–4.1 ms。猜错只影响速度,
  不影响答案。
- 依据:记录了 1,190 次猜测。被主干接受的猜测中,72% 是对话里出现过的 token;加上主干每一行输出里
  最大的 256 个之后覆盖 98%。主干本来就要算这些行。
- 做法:把这些行记成清单(一个回答后约 1.3 万行,整层的 5%),猜测只乘清单上的行。清单在对话之间保留,
  超过 4.8 万行清空重来。挑"最大的 256 个"由 GPU 在 CPU 准备草稿时顺带完成,下一步才进清单。
- 实测(固定猜 3 个,与算全部行交替):Q2_0 +2% 到 +10%(中位约 6%),IQ3_S +4% 到 +12%(中位约 8%),
  每次验证产出的 token 数不变。启动后的第一个回答清单还短,没有收益。

### 3.3 一步之内的内核

**残差连接:一个窗口只读一遍权重**(`fused.py`,实验 e07–e09)
- 每层两次残差连接,权重 1.27 GB。重写成三个内核:权重读一遍,同时算窗口里所有 token;每个线程只做
  十来个权重。
- 学到的两条规律:一个内核的耗时等于它最慢的那个线程;线程内的局部数组慢 6 倍。
- 实测:4-token 窗口 −1.8 ms。

**Q2_0 专家:查表代替乘法**(`blocks.lookup_matvec`,实验 e02、e03、e10–e12)
- 专家内核不是被字节数限制,而是被运算量限制:每个权重约 8 次运算,怎么改内层循环都一样。
- 两个 2-bit 权重对两个输入只有 16 种"和"。每个 token 先把这 16 种和建成表(41 KB,放得进缓存),
  之后每两个权重查一次表,每个权重约 3 次运算。四个权重一张 256 项的表放不进缓存,反而慢 4 倍。
- 实测(整步):1 / 2 / 4 / 8 个 token 分别 −0.4 / −1.2 / −3.4 / −9.4 ms。只对 Q2_0 加 16 位浮点有效。

**去掉不必要的等待**(实验 e14 等)
- 上下文 token 原来放在 GPU 上,每步要等两次才能取到;每步留给下一步的状态也在白等。改成放 CPU、
  不等。每步 −3.6 ms(一步 41 ms)。
- n-gram 表的行号改在 CPU 上算:单 token −0.4 ms,4-token −0.75 ms。
- 路由器的矩阵乘直接读 16 位权重、32 位累加:每步 −0.7 ms。

**每层的两半各编译成一个函数**(`engine._fuse`)
- 把连续的逐元素运算合并成一个内核。单 token 28 → 24 ms。这是早期做的;后来知道它的收益有限
  (见第 2 节)。

### 3.4 读提示

- **分块读,输出层只算最后一个 token**:每块 2,048 个 token。
- **对话只读一遍**:在消息边界存检查点,后续消息只读新增部分;可存盘恢复。
- **被打断的对话不重读**(`conversations.py`,做法取自 Strata,在这里重写)。原来引擎只持有一段对话、保留
  最新的 8 个检查点:来一个不相干的请求(客户端自动发的"生成标题"、另一段聊天),这段对话就被截回公共
  前缀,下一轮要把分叉点之后的内容全部重读。现在分两层:
  - 检查点的去留(默认生效):从头读的提示,在第一条消息结束处(系统提示的结尾,满 2,048 token 时)存
    一个检查点,它是所有请求共享的"根",永远保留;其余按最久未用淘汰,提示末尾前一个 token 处的那个
    最先走。请求可以用 `ckpt=0` 表示"没有后续请求",用 `pin=N` 钉住一个共享前缀。
  - 停放整段对话(`--conversation-cache-mib`,默认关):提示在最后一轮开始之前就和当前对话分叉时,把
    当前对话整段停放在内存里;之后有提示接着它说,就整段取回。只是数组换手,不做计算,停放和取回各 0.3 ms。
  - 实测(Q2_0,M4 Max,经行协议):系统提示 2,760 token,对话 A 带一份文档共 9,991 token,中间插一个
    34 token 的标题请求和共用系统提示的对话 B。A 的第二轮出第一个字:不停放 19.7 秒(整段重读),停放
    0.26 秒(10,057 token 里 10,038 不用读);A 的第三轮 15.3 秒对 0.25 秒。B 作为新聊天从系统提示之后
    读起,0.2–0.3 秒。
  - 答案:32 位浮点下,同样的提示开不开停放答案逐 token 相同(两段对话交替共九个请求)。16 位浮点下
    不保证:九个里有三个出现分歧。分歧处没有逐个去看;32 位下完全一致,说明是舍入:"接着对话停下时
    的状态往下写"和"把对话重读一遍"舍入不同,和窗口与单 token 舍入不同是一回事。不开停放时,普通的
    后续消息也有同样的性质(见第 5 节)。
  - 代价:停放的对话占内存,每 token 30 KB,每个检查点 110 MiB(10,038 token 带三个检查点是 732 MiB;
    停放时只留根、被钉住的和最后两个检查点,所以一段 10,194 token 的对话聊了五轮仍是 738 MiB);
    这笔预算在算专家份额之前先从机器内存里扣掉。
- **专家的配对在 GPU 上排序**(`blocks.tiles_of`,实验 e30–e32):读一块提示时,每层要把"token × 选中的
  专家"按专家归到一起再乘。原来在 CPU 上排,所以每层都要停下来等 GPU 把路由结果算完,停顿之后的计算也
  变慢。实测一块 1,024 token 花 2.7 秒,其中专家只需要 1.0 秒;把排序结果预先给它,同一块只要 1.8 秒。
  现在用数组运算在 GPU 上排:格子数按"最多可能需要多少"分配,用不到的格子内核直接跳过。
  376 → 559 tok/s(Q2_0,1,024 token 一块)。
- **专家直接从文件数据块按格乘**(`blocks.tile_matmul`,实验 e33):一格是一个专家的 16 个 token × 64 行。
  线程组把这 64 行的 64 列解到线程组内存里,Apple 的着色器内矩阵乘法(Metal Performance Primitives 的
  `matmul2d`)拿它当操作数去乘这一格的 token,再换下 64 列。九种格式通用,16 位和 32 位浮点都支持。
  - 一次乘法(10,220 对)4.5–5.4 ms,6.3–7.4 T 次/秒,与格式无关。
  - 它替换了两条旧路径:Q2_0 的"拆成编码和系数 + 2-bit 操作数"(一层 22 → 16 ms),以及其他格式的"整堆
    展开成 1.7 GB 浮点再用 MLX 的 gather_mm"(IQ3_S 文件一层 43–79 → 16 ms)。
  - 32 个 token 一格、或一次解 128 列,都慢约两成;一次解 256 列(用满线程组内存)在真实尺寸上结果是错的。
- **结果**(带草稿头,端到端,各读三次):

  | 提示长度 | Q2_0 | IQ3_S |
  | --- | ---: | ---: |
  | 1,180 token | 555–560 tok/s(之前 370–386) | 488–513(之前 334–349) |
  | 2,620 token | 652–653 | 633–639 |
  | 8,668 token | 420–507 | 455–614 |

  最长一档越读越慢:每次要满载 15–20 秒,机器自己降速(第 7 节)。读提示时高出常驻的内存峰值:Q2_0
  2.5–4.0 GB,IQ3_S 5.6–7.1 GB(其中 3.3 GB 是第一次读提示后保留的 Q6_K 浮点权重)。小内存模式读
  1,537 token:这里原来写的"273–287 tok/s(之前 136–159)"是错的,那次测量时模型文件在系统的文件
  缓存里,替磁盘作了答;清掉缓存后是 146–171 tok/s,见 3.6 节。
- **切换点**:1,600 对(约 160 个 token)以上按格乘,以下一对一对地算(Q2_0 查表,其他格式用逐行内核)。
  一格里只有 1 对和有 16 对成本一样,短块里每个专家分不到几个 token。
- **还剩什么**:专家现在占一块提示时间的一半(49–54%),4.9–6.1 T 次/秒;其余部分单独跑相当于
  1,200 tok/s。1,024 token 时仍有 26% 的格子是填充。
- **没查的一个现象**:短块在空闲之后特别慢。64 个 token 连续读是 179 ms,空闲 2–8 秒后是 430–580 ms;
  单 token 解码不受影响(21 ms),256 个 token 影响很小。几十 token 的问题因此要多等约 0.3 秒才出第一个字。
- **走过的弯路**:开始以为慢在乘法本身(e30 量到专家占 71%、只有 2.3 T 次/秒),准备直接写新内核。先把
  这部分再拆开量(e31),才发现乘法已经和 MLX 自带的分组乘法一样快(7 T 次/秒),时间丢在每层的停顿上。

### 3.6 小内存机型(16 / 24 / 32 GB)

(`paged.py`)只把一部分专家留在内存,其余按需从 SSD 读;按机器内存自动定预算。在 128 GB 机器上限制
预算测得(Q2_0,带草稿头,服务进程实测):16 GB 11–12 tok/s,24 GB 18–27,32 GB 23–38;读 1,180 token
的提示 107–145 tok/s。详见 `ROADMAP.md` 最后一节。

**真机数据与留给 macOS 的内存(issue 6)。** 上面三档是在 128 GB 机器上把专家预算限制为 3.3、11.9、20.5 GB
测的,当时规则给 macOS 留 4.5 GB。第一台真实的小内存机器(MacBook Air M5,32 GB)按这个默认值会大量换页:
专家 20.5 GB 时一次运行换出 106 GB,答案 5.8–19.2 tok/s;专家 16 GB 时 23.4–26.8,关掉其他程序后
24.3–28.8,几乎不换页。各次运行里数组峰值都是专家预算加约 8.5 GB,与规则的估算一致;不够的是留给系统的
部分:什么都不开时 macOS 自己占 6.1 GB。在 128 GB 机器上限制预算测不出这一点,因为那里没有内存压力。
现在给 macOS 留 8.5 GB:32 GB 机型的专家是 16.2 GB,24 GB 机型 7.6 GB,16 GB 机型只剩最低的 0.5 GB(`--check` 报“太小”)。
(之后工作内存从 4 GB 改为 5 GB,见下文按层读提示:现在是 15.2 和 6.6 GB。)
那台机器按新默认值又跑了两次:关掉其他程序换出 0.89 GB,开着应用换出 16.8 GB(启动前空闲 11.5 GB,另一次是
24.5 GB)。固定的常数管不住别的程序占了多少,所以加了 `--expert-memory available`:专家的份额不超过启动时
"空闲 + 文件缓存"减去工作内存。按那两次的 `vm_stat`,开着应用时约 8 GB,关掉时仍是规则给的数。目前是可选
参数,不是默认。那台机器开着应用跑了两次(第一版):专家 14.0 和 15.1 GB,换出 1.70 和 0.41 GB,回答 21.6 和
24.8 tok/s(固定默认值那次是 16.5 GB、16.8 GB、18.3 tok/s)。他每 2 秒的采样指出第一版数错了:它在加载之后才
数,而加载刚把约 9 GB 的模型文件读进了文件缓存。现在改为加载之前数,再减去已加载的量和工作内存;按这个
算法,第一次(启动时只有 0.9 GB 空闲)专家应是 5.8 GB 而不是 14.0 GB。那次启动后不久退出了一个应用,所以
哪个数对还没有干净的验证。
依据只有这一台机器;上面三档的速度没有按新的预算重测。

**稠密层直接在文件数据块上算(实验 e36)。** Q2_0 文件的稠密张量在文件里是 3.64 GB,装进内存是 5.49 GB:
MLX 只能用 8 位来存 Q3_K 和 IQ4_XS 两种格式,多出来的 1.85 GB 里有 1.74 GB 出在这两种格式上(91 个 Q3_K
张量多 1.25 GB,其中词嵌入表 0.44 GB;56 个 IQ4_XS 张量多 0.49 GB)。小内存模式下这两种格式现在按文件
原样放进内存(`dense.BlockLinear`、`BlockEmbedding`),省下的 1.74 GB 全部给专家;内存放得下整个模型的
机器不变。

| 机型 | 稠密层形式 | 内存里的专家 | 回答 tok/s(均值) | 每 token 要读的专家 |
| --- | --- | ---: | ---: | ---: |
| 16 GB | 原来(MLX 数组) | 1.59 GB | 6.4–7.7(7.2) | 352–431 |
| 16 GB | 数据块 | 3.33 GB | 9.5–11.8(10.9) | 193–211 |
| 24 GB | 原来 | 10.18 GB | 14.9–25.4(两轮均值 19.2、23.3) | 40–80 |
| 24 GB | 数据块 | 11.92 GB | 17.5–29.0(两轮均值 20.3、26.4) | 32–65 |
| 32 GB | 原来 | 18.77 GB | 21.1–41.7(两轮均值 33.3、36.5) | 11–32 |
| 32 GB | 数据块 | 20.51 GB | 23.8–40.4(两轮均值 33.2、35.5) | 10–34 |

(`bench/paged.py --machine-memory <GiB> --dense arrays|blocks`,四段对话各 200 token 跑两遍,先清掉文件
缓存;24 和 32 GB 两档按相反顺序又跑了一轮。)

- 16 GB 机型快了一半:内存里的专家翻倍,要读的专家减半。
- 24 GB 机型两轮分别快 6% 和 13%,比同一种形式两轮之间的差别还小。
- 32 GB 机型没有差别:少读一成,每遍多算约 1 ms,互相抵消。
- 速度代价(一遍里这两种格式的全部 146 个乘法,数据块对 MLX 数组):1 个 token 3.8 对 4.7 ms,4 个 token
  5.6–5.7 对 4.8 ms,8 个 token 9.3–9.4 对 7.4–7.5 ms。读提示时每块临时解包再乘:1,024 token 一块
  290–307 ms,MLX 数组 310–312 ms,按专家的分格方式 423–454 ms。
- 正确性:3.3 GB 专家在内存时,与 llama.cpp 已保存答案的首选 token 在 1,537 和 3,161 token 两个提示上都是
  64/64(逐 token 和四个一遍),与数组形式相同;32 位浮点模式对 Metal 答案 64/64,对 CPU 答案 63/64,也与
  数组形式相同。

**更正:小内存模式读提示的速度。** 之前记录的"1,537 token 读 273–287 tok/s"是在模型文件已经在系统文件
缓存里的情况下测的:即使按"绕过缓存"的方式读,只要数据在缓存里,系统仍然从缓存给。同一个脚本、3.3 GB
专家在内存:文件在缓存里时 255–277 tok/s,清掉缓存后 149–162 tok/s。一千个 token 的一块提示几乎用到每层
的所有专家,所以每层整层读,一块要从磁盘读 30 GB,耗时 8–11 秒。清掉缓存后,1,537 token 在 16 / 24 / 32 GB
机型上:数组形式 146–171 tok/s,数据块形式 160–182 tok/s,第一版是 136–159。也就是说,读提示那次改动在
小内存机型上只快了约一成,不是一倍;这里读提示受磁盘限制。

**提前读专家:量过,没做(实验 e35)。** 用下一层的路由器提前一层去猜,真实选中的 10 个专家有 77% 在猜的
前 10 名里,89% 在前 16 名里。但提前读只能把读盘和 GPU 计算重叠起来,不能让读盘变少:16 GB 机型上磁盘占
回答时间的三分之二,估算上限是 1.35 倍,24 GB 机型 1.39 倍,低于事先定的 1.5 倍;slotstream 在真机上做同样
的事实测是 1.1 倍。"提前读上一个 token 用过的专家"没有用:它们本来就在内存里。能让读盘变少的是让更多专家
留在内存。

**读提示时每层专家只读一次(实验 e37–e40,`bylayer.py`)。** 小内存模式下提示按 2,048 token 一块读,
每块走完所有层,每块都把每层的专家从盘上读一遍且不保留,所以多块的提示在重复读(e37)。现在要读的新 token
超过一块时改为按层读:提示按 8,192 token 一段,每段逐层走,每层专家只读一次并留到该层走完;算这一层时
后台线程整层读下一层。每块在每层的计算不变。一块以内的提示走原来的代码。

Q2_0,float16,模拟 32 GB 机型(内存里按服务端的做法放 15.9–16.4 GB 最常用的专家),每次读前清文件缓存,
三种读法交替各三遍、两次读之间停 10 秒,取中位数(e40):

| 提示 | 原来(逐块) | 按层读 | 按层读并提前读下一层 |
| ---: | ---: | ---: | ---: |
| 1,537 token(一块,代码未变) | 6.3 秒 | 6.2 | 6.6 |
| 2,560 | 10.5 | 9.5(1.11 倍) | 8.8(1.20 倍) |
| 4,096 | 15.1 | 12.3(1.22) | 9.7(1.56) |
| 8,192 | 32.4 | 22.8(1.43) | 19.2(1.69) |
| 32,768(各一遍) | 192.9 | | 116.8(1.65) |

- 8,192 token:读盘 70 GB → 34 GB;提前读之后提示总共只等盘 0.2 秒。
- 事先定的两道门槛都过了:第一阶段 1.43 倍(要求 1.3),整体 1.69 倍(要求 1.5)。另一轮两次读之间只停
  3 秒、机器逐渐降速的运行给出 1.64 和 1.53 倍:数字随机器状态的波动比第二阶段的收益还大。
- 正确性:每个提示在三种读法下的状态摘要(对话的全部数组、检查点、第一个 token、草稿头的猜测、16 个回答
  token)完全相同。测试(`tests/test_bylayer.py`,float32 和 float16)要求逐位相同,包括 `ckpt=0`、`pin`、
  多段提示;在段内任意一步取消后回滚,状态与段开始前相同,再读一遍与从未取消相同。
- 取消:每一步(一块过半层)可停,最长一步 0.26–0.30 秒;原来要等一整块(约 8 秒)。被取消的那一段作废,
  之前读完的段保留。
- 内存:8,192 token 的一段,数组峰值比原来高 0.9–1.1 GB(3.90 对 2.82–3.03 GB),所以规则里的工作内存从
  4 GB 改为 5 GB:32 GB 机型的专家 16.2 → 15.2 GB,24 GB 机型 7.6 → 6.6 GB。上表是改之前测的。
- 32,768 token 的提示读完且状态一致,峰值比静止时高 5.00 GB(原来 3.72 GB)。那次运行里有一步用了 10.4 秒,
  再跑一遍逐步计时最长只有 0.28 秒,原因不明。
- 与设计不同的一处:不提前读时,一层不总是整层读。两块的短段每层只用到 303–396 个专家(共 512),而内存里
  已有一半专家的机器按专家读只要 18–19 GB,整层读是 34 GB;所以那时按块的需要读,读到的留到该层走完。
- 没做的:只读内存里缺的专家(32 GB 机型每段 34 GB 里的 18 GB),在慢盘上才有用;IQ3_S 没这样读过。
- 更正:之前记的"macOS 上 2 MB 以上的读会经过文件缓存"不成立。读进按页对齐的缓冲区(`preadv`)时 16 MiB
  一片也不进缓存;返回 `bytes` 的 `os.pread` 才会(4 MiB 一片,5.66 GB 里 4.23 GB 留在缓存)。
- **上表的前提:n-gram 表在系统文件缓存里。** e37–e40 每次读之前只清了专家所在的那个文件,另一个文件是
  28.8 GB 的 n-gram 表,引擎把它留在盘上、靠缺页读。32 GB 的机器放不下这份缓存。经行协议、两个文件都清掉
  (`bench/prompt_by_layer.py`,8,192 token,四次的中位数):逐块 46.9 秒,按层读 38.0(1.24 倍),加提前读
  36.2(1.30 倍);只清专家文件时是 33.6、25.0(1.34)、22.3(1.51)。冷读这张表每 8K token 多 13–14 秒,
  三种读法都要付。按"读前清文件缓存"的字面,整体是 1.30 倍,没有到 1.5;它在每一对比较里都不慢,仍保持
  默认开启。
- **n-gram 表的行改为并行预读(`load.PleTable._ahead`)。** 一次查 256 行以上时,先抽 64 行看是否在缓存里;
  不在就用 32 个线程把这些行所在的页读进来,再照常查表。一块 2,048 token 的行:靠缺页 6.3–6.4 秒,预读
  0.22 秒;表在缓存里时两种都是 0.01 秒。同样的提示、两个文件都清掉:逐块 35.4 秒,按层读 28.6,加提前读
  25.6(1.38 倍;第二轮机器降速)。和这之前的逐块读法(46.9 秒)相比,现在是 1.8 倍。写回答时每次查的行太少,
  不走预读,冷表对回答的影响没有量。
- **真机(issue 6 的 32 GB MacBook Air M5,报告者自己跑的 `bench/prompt_by_layer.py`,两个文件都清):**
  8,192 token 逐块 45.7 秒,按层读 34.5(1.32 倍),加提前读 31.5(1.45 倍),每次答案相同。六次启动共换出
  8.1 GB,和读法看不出关系。
- **第二台真机(issue 8,64 GB 的 M5 Pro,报告者自己跑的,`8a5aeaa`):** IQ3_S 在这台机器上按规则留 93% 的
  专家在内存。8,192 token:逐块 37.85 秒,按层读 24.9,加提前读 19.1(1.98 倍),各种读法输出相同。对话停放:
  1 万 token 的对话被打断后下一轮出第一个字,IQ3_S 23.4 → 0.68 秒,Q2_0 13.8 → 0.24 秒(4,096 MiB;8,192 MiB
  没有更好),27 次续写都保住了对话里的事实。仍然慢的:IQ3_S 读 1,180 token 的提示只有 61–67 tok/s,回答
  17–44 tok/s。一块以内的提示在用到某层 384 个以上专家时会把该层整层从盘上读一遍(代码类提示 48 层里有 30–31 层),
  包括内存里已有的 93%(之前写成"每层都整层读",不准确)。PR 7 之后只读内存里缺的:模拟 64 GB 跑 IQ3_S,1,180 token
  的提示从读 32 GB、7.2–8.0 秒降到读 1.4 GB、3.3–3.9 秒(作者在 M5 Ultra 上测)。
  内存:规则判定能整个装下的一个 IQ3_XXS 文件在一次运行里换出 7.4 GB,原因未明。
- 其余数字都在一台 M4 Max(盘 6.5 GB/s)上模拟小内存机器测得,没有真实的内存压力,也没有慢盘的数据。

**PR 7(vendyluo,在 M5 Ultra 上测)。** 四个提交照原样合入:
- 空闲后的短提示(issue 1):GPU 空闲约 2 秒后会放掉未锁定的数组,约 4 秒后休眠;只锁定不保持清醒反而最慢。现在
  请求后 600 秒内每秒给 GPU 一个很小的运算,同时锁定数组,窗口结束时放开,下一个请求跑完后再锁上
  (`--keep-awake`、`--wired`)。本机 Q2_0 经服务端、请求间隔 8 秒:27–49 token 的提示 618–835 → 148–215 毫秒,
  340 token 832–934 → 692–751,1,180 token 2,113–2,630 → 1,829–1,874;回答速度不变。空闲时 GPU 多耗中位数 12 毫瓦。
- 为读提示保留的浮点数计入内存规则(issue 3)。
- 整层读时内存里已有的专家不再重读(issue 4),见 3.6 节。

**给 macOS 留内存的四分之一(10 月 14 日)。** 一台 48 GB 的 M4 Pro 跑 Q2_0(X 上 @yuanhao 的报告):按原规则给专家
30.1 GB 时,启动阶段换出 4.98 GiB;限制在 24 GB 后不再换页,Strata 自己的 Metal 版在那台机器上选了 25.6 GB。
现在留给系统的是内存的 25%,至少 8.5 GB:32 GB 机型不变,48 GB 机型 Q2_0 的专家 82%(原来 95%),64 GB 机型 IQ3_S 76%
(原来 93%,而 #8 那台在 93% 时没有换页,可能偏保守),Q2_0 从 58 GB 起整个装下(原来 51)。依据只有两台机器。

## 4. 试过但无效的

记下来是为了不再重走。

| 方向 | 结果 |
| --- | --- |
| 合并小内核以减少内核数 | 内核数 −43%,时间 −15%;瓶颈不是内核数 |
| MLX 的调度开关(命令缓冲区大小、快速同步等四个环境变量) | 无变化 |
| 专家内核一次读 4 个值,或一个线程算多行 | 无变化:瓶颈是运算量 |
| 稠密层直接读文件的 Q3_K 数据块 | 与 MLX 的 8-bit 乘法打平(74/80/91 对 77/78/81 微秒) |
| Q6_K 直接读文件数据块 | 1–2 个 token 更快,4 个以上更慢;改用每权重 1 字节 |
| 给草稿头用低位数的输出层副本 | 每次只省 0.2–0.4 ms,3–14% 的猜测会变 |
| 用压缩"草图"筛选输出层的行 | 要找回 99% 的正确猜测得算整层的五分之一 |
| 按"离最大值的距离"而不是固定个数来列清单 | 没有明显胜者的行会一次列进几万行 |
| 小内存机型启动时预装最常用的专家 | 几乎无效:一段对话要用的专家和"总体最常用的"关系不大 |
| int8 路径 / Metal 4 打包权重用于解码 | M4 上整数并不比 16 位浮点快;只对读提示有小收益 |
| CPU 分担专家计算(Strata 在 PC 上的做法) | 统一内存下 GPU 能直接读全部权重;同样的活 CPU 慢一个数量级 |

还有一项**测了但没做**:把残差连接的权重从 16 位压到 8 bit,每步再省约 1.6 ms(5–8%)。它会改动权重,
7K 长提示上与 llama.cpp 的一致率从 64/64 降到 62/64。本项目至今没有改过任何权重。

## 5. 正确性与输出质量

**与 llama.cpp 对比**(同一文件,首选 token 是否相同,64 步):
- Q2_0:对话提示 64/64;7K 提示 63–64/64;32K 提示 64/64。
- IQ3_S:对话提示 63/64(llama.cpp 自己的 Metal 与 CPU 两个后端之间是 64/64,对数概率中位差 0.09;
  本引擎对两者是 0.05 和 0.09)。
- 注意:要用模型会正常作答的对话提示来比。强制越过结束符续写时,llama.cpp 自己的两个后端也只有
  前 7 个 token 相同,比不出任何东西。

**输出质量**(实验 e29):用"32 位浮点、逐 token、不猜"的模型当裁判,逐个检查各模式写出的每个 token
是不是裁判在同样上文下的首选。

| 模式 | Q2_0(1,024 个 token) | IQ3_S(986 个 token) |
| --- | ---: | ---: |
| 16 位,逐 token | 1,020 | 982 |
| 16 位,草稿头 | 1,018 | 981 |
| 16 位,草稿头 + 行清单(默认) | 1,020 | 981 |
| 32 位,草稿头 + 行清单 | 1,024 | 986 |

- 16 位下大约每 250 个 token 有 1 个不是模型的首选,带不带草稿头、用不用清单都一样;都出现在两个候选
  接近的位置(多数差 1–3 个百分点,最大一处是 44.6% 对 38.0%)。之后的文字会因此不同。
- 32 位下 8 个回答全部与精确模型一致。`--dtype float32` 的代价:Q2_0 约慢一半(44–49 对 80–103 tok/s,
  因为查表内核只支持 16 位),IQ3_S 只慢一到两成(53–73 对 69–80 tok/s)。
- 样本是 4 个提示、每个规格约 1,000 个 token,"每 250 个 1 个"是量级估计。

**测试**:231 个,覆盖每种权重格式对参考解码、窗口与逐 token 结果一致、各种猜对猜错组合下答案不变、
采样时同种子同文字、行协议、存盘恢复等。

## 6. 这台 GPU 能做什么(实测)

- 大矩阵乘法(4096³):MLX 16 位浮点 14.3–14.7 T 次/秒,与 Apple 自己的 Metal 4 矩阵原语(14.3)相同。
  int8 是 12.8,2-bit 打包权重是 13.4:整数路径在 M4 上并不更快。
- 内存读取约 470–480 GB/s。
- CPU(SME2,Accelerate)约 3.3 T 次/秒,是 GPU 的四分之一。
- Strata 在 RTX 5070 上读 Q2_0 的提示是 2,650 tok/s,本引擎现在是 555–650,差约 4–5 倍(改之前约 7 倍)。
  之前写的"主要来自硬件"不对:改之前有近一半时间丢在每层的停顿上,是软件的问题(见 3.4)。现在专家的
  乘法在 5–6 T 次/秒,稠密层在 10,GPU 做一个大乘法是 14.3。
- M5 的 GPU 带神经加速器,MLX 和 llama.cpp 都已有针对它的内核;这里没有 M5,未测。

## 7. 测量方法与注意事项

- **这台机器会自己降速。** 固定的 4096³ 乘法静止时 14.5 T 次/秒,满载 20 秒后降到 12,约 80 秒后系统
  散热状态从 nominal 变成 fair;长基准中途测到过 9 以下。停下十几秒恢复。同一个测试因此能相差 25–50%。
- 所以:
  - 判断一项改动是否有效,用同一进程内新旧交替(每步或每个提示交替),比较中位数或下四分位数。
  - 前后对比的 tok/s,按提示逐个交替、每次一个进程。
  - 连续跑几分钟得到的绝对 tok/s 只能当范围看。
- 单独测一个部件得到的时间加不起来等于整步时间。部件的代价用"从真实的一步里拿掉它"来量(e06)。
- 本文早期几组 IQ3_S 的数字(25–27 / 36–49 tok/s)是在降速状态下测的,已作废。
- 环境变量 `MTL_DEBUG_LAYER=1` 会让 llama.cpp 在这个模型上崩溃,基准脚本都会去掉它。

## 8. 没做的和已知限制

- 16 位浮点下不保证"带不带草稿答案逐 token 相同"(见第 5 节);32 位下成立。
- IQ3_XXS、IQ2_XS、Coder 等其他文件没有跑过(磁盘空间)。加载器对它们的张量都有路径,格式通过了同样的测试。
- 350 token 以下的提示读得不比 llama.cpp 快(27–49 token:31–112 对 92–148 tok/s),空闲后第一块还会
  额外变慢,原因未查(3.4)。
- 停放的对话只在内存里,重启就没了;没有"空闲内存低于某值就不停放"的下限(Strata 有)。
- 小内存机型只有一台 32 GB 真机的数据(3.6);每层要等路由结果,即使不读盘每 token 也多约 10 ms。
- 图片输入、多对话并行没有实现。
- 对话缓存每 token 约 30 KB(128K 上下文 3.9 GB),没有压到 8 bit。
